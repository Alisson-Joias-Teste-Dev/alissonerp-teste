## Story

**As a** desenvolvedor responsável pela integridade transacional do ERP,
**I want** que toda venda crie suas ordens de reposição **dentro da mesma transação** e que o sync com Tiny seja desacoplado via fila assíncrona,
**so that** falhas em sistemas externos não corrompam dados do banco e operações compostas (venda + reposição) sejam atômicas.

## Acceptance Criteria

1. **AC1:** Tabela `alissonerp.fila_sync_externo` criada via migration aditiva: `id BIGSERIAL PK`, `sistema VARCHAR(50)`, `payload JSONB`, `status VARCHAR(20) DEFAULT 'pendente'`, `tentativas INTEGER DEFAULT 0`, `ultimo_erro TEXT`, `criado_em TIMESTAMPTZ DEFAULT NOW()`, `processado_em TIMESTAMPTZ`. Index `(status, criado_em)`.
2. **AC2:** Em `src/app/api/contatos/route.ts`, sync com Tiny é substituído por **INSERT na fila dentro da transação** que cria o contato — não é mais `syncContatoToTiny(...).catch(...)` em background.
3. **AC3:** Em `src/app/api/vendas/route.ts`, criação de ordens de reposição é movida para **dentro do `sql.begin()`** principal da venda. Se ordem falhar, a venda inteira é revertida (rollback).
3a. **AC3a (NOVO v1.1):** As 7 rotas multi-tabela críticas adicionais (descobertas na validação técnica) também são envolvidas em `sql.begin()`:
   - `POST /api/pcp/apontamentos` (apontamentos_pcp + pcp + movimentacoes_estoque + insumos)
   - `POST /api/pcp/transferir` (distribuicoes + movimentacoes_estoque ×2)
   - `POST /api/distribuicao/[id]/saida` (distribuicoes + movimentacoes_estoque + insumos + apontamentos_pcp)
   - `POST /api/service/[id]/transferir` (servicos + movimentacoes_estoque)
   - `POST /api/devolucoes` (devolucoes_venda + itens_venda + estornos)
   - `POST /api/pcp/[id]/atribuir-operador` (pcp + movimentacoes_estoque)
   - `POST /api/distribuicao/[id]/concluir` (verificar e adicionar tx se faltar)
4. **AC4:** Teste integration: força erro no INSERT da ordem de reposição → venda **não persiste** no banco (`SELECT COUNT FROM vendas_erp WHERE ...` retorna 0).
5. **AC5:** Teste integration: força erro no Tiny → contato persiste no banco com item correspondente em `fila_sync_externo` com `status='pendente'`.
6. **AC6:** Worker básico de fila implementado em `scripts/processar-fila-sync.ts` (executável via cron). Processa itens `status='pendente'` e marca como `processado` ou incrementa `tentativas`. Retry/exponential backoff completo fica para Story 3.4.
7. **AC7:** Endpoint `/api/admin/fila-sync` (GET) retorna lista paginada da fila com filtros (status, sistema). Acesso restrito a `desenvolvedor|admin`.
8. **AC8:** `npx tsc --noEmit` passa. Smoke test em homolog: criar contato + criar venda completa, conferir banco + fila.

## Dev Notes

- **Pegadinha CLAUDE.md §3:** `sql.begin()` callback parameter usar `tx`, **NÃO** `sql` (conflito de tipo).
- **Pegadinha:** `syncContatoToTiny` original usa `.catch()` para não bloquear retorno 201. Esse comportamento vai sumir — agora INSERT na fila acontece **dentro** da tx, e o sync real é diferido para o worker.
- **Cuidado vendas:** A criação de ordens (atualmente fora da tx) referencia o `id` da venda recém-criada. Mover pra dentro da tx exige usar `tx` (não nova conexão).
- **Se algo der errado:** Migrations são aditivas. Refactor é reversível por commit revert.
- **Story 3.4 expande:** retry exponencial (1m, 5m, 15m, 1h, 6h), alerta após 5 tentativas, dashboard.
