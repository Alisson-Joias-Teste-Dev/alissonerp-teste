# Auditoria do Sistema Alisson ERP — 2026-05-16

> Análise read-only, zero código/banco tocado. Resultado de 4 varreduras paralelas (DB, API routes, frontend, cross-cutting).
> Módulo `orçamento` já passou por hardening completo (v2.43.0) — não reanalisado.

---

## TL;DR — o que dói mais agora

Em ordem de **gravidade real para a operação/segurança da joalheria**:

1. **~50 rotas administrativas usam `user.user_metadata?.role` em vez de `alissonerp.usuarios.role`** — qualquer usuário pode setar role no metadata via `auth.updateUser({ data: { role: "admin" } })` e virar admin. **Escalada de privilégio trivial.**
2. **~25 rotas sem auth nenhuma** — incluem criar/revogar API keys, lançar movimentação de ouro, criar compras, sobrescrever chave de IA, aprovar consultoras, concluir entregas.
3. **Várias rotas autenticadas confiam em `user_id`/`user_role` vindos do body** (purificação, distribuição, lançamentos avulsos) — bypass + fraude de audit trail.
4. **Webhook Focus NFe sem validação de assinatura** — qualquer um marca NFe como autorizada via POST.
5. **Webhook Mercado Pago faz fallback para "admin mais antigo"** como autor — audit trail mente; imprestável para investigação de fraude.
6. **Coluna `pagamentos_venda.ouro_peso` vs `ouro_gramas`** com dados parciais em cada — pagamento em ouro pode estar duplicando/perdendo registro.
7. **Migrations 178 e 181 são quase idênticas e fizeram BACKFILL DIFERENTE** sobre `source` em `pagamentos_venda` — histórico financeiro corrompido.
8. **38 migrations com o mesmo número** (e.g. 3 arquivos `138_*`) — ordem de execução não-determinística.
9. **Sync `public.vendas` ↔ `alissonerp.vendas_erp` tem drift de 104 linhas** e foi corrigido 4× via triggers; **gap de ~50% em `itens_venda`** entre os dois schemas.
10. **Geração de `numero_ordem`/SKU/EPC RFID via `MAX(...) + 1`** em 10+ pontos — race condition sob carga, EPC RFID duplicado quebra rastreamento.

Há **~30 problemas CRÍTICOS, ~25 ALTOS** totais (detalhe abaixo).

# 1. CRÍTICOS — perda de dinheiro/dado, segurança

## 1.1. Segurança & Auth

### S1. `user_metadata?.role` aceito em ~50 rotas administrativas (RBAC bypass)
**Padrão errado:** `if (user.user_metadata?.role === "admin")`. Supabase permite ao próprio usuário escrever em `user_metadata`. Basta `await supabase.auth.updateUser({ data: { role: "admin" } })`.

CLAUDE.md exige: *"Fonte de verdade: alissonerp.usuarios.role"*.

**Top rotas atingidas (lista completa no audit bruto):**
- `src/app/api/admin/api-chaves/route.ts:16` + `[id]/route.ts:15` — gera/revoga API keys
- `src/app/api/configuracoes/roles/route.ts:16` + `[nome]/route.ts:12` — edita roles
- `src/app/api/configuracoes/permissoes/route.ts:131`
- `src/app/api/configuracoes/parametros/route.ts:10` — PARAMETROS_SISTEMA (depósito, insumos)
- `src/app/api/produtos/route.ts:80,483` + bulk-edit + sync-erp-to-public + sync-public-to-erp
- `src/app/api/precificacao/*` — quase todas (aprovar, rejeitar, markup, cotações)
- `src/app/api/site/*` — sync, config, produtos, invalidar-cache
- `src/app/api/fornecedores/route.ts:20,93`
- `src/app/api/pcp/ordem-teste/route.ts:19`
- `src/app/api/produtos/pedras-bulk/*`, `peca-avulsa`, `normalizar-metal`, `rename-metal`, `classificar-tipo`
- `src/app/api/insumos/route.ts:27,78`

**Fix:** trocar todas por `requireAuth()` ou `defineRoute({ requireRoles: [...] })`. Já existe em `src/lib/auth-server.ts` e `src/lib/api-handler.ts`.

### S3. Webhook Focus NFe não valida assinatura
**Arquivo:** `src/app/api/fiscal/webhook/focus/route.ts`

### S4. Webhook Mercado Pago aceita HMAC inválido em "fallback"

**Fix:** exigir HMAC válido também em simulação.

### S5. `getSystemUserId` finge autoria com admin "mais antigo"
**Arquivo:** `src/app/api/webhooks/mercado-pago/route.ts:35-60`
Quando `mp_system_user_id` não está configurado, webhook usa o admin mais antigo do sistema como autor de transições de venda/contas-receber. Audit trail mente.
**Fix:** falhar loud (HTTP 500 + log) até `mp_system_user_id` ser configurado.

### S6. Rotas autenticadas que aceitam `user_id` do body (fraude de audit trail)
**Arquivos:**
- `src/app/api/distribuicao/apontamentos/route.ts:11-31,67-78` — autentica, mas grava `body.user_id` no INSERT e `logAudit`
- `src/app/api/purificacao/**` — vários
- `src/app/api/distribuicao/[id]/saida/route.ts:40-49,183`
- `src/app/api/lancamentos-avulso/route.ts` — `created_by` do body sem autenticar

**Impacto:** "Toda grama conta" (CLAUDE.md §3) — quebra rastreabilidade de ouro. Atacante posta `user_id` de outro funcionário e log mostra nome dele.
**Fix:** sempre usar `authUser.id`; nunca aceitar `user_id` do body.

### S9. Fotos de ordem/cofre em URL pública direta (CLAUDE.md exige signed URL)
**Arquivos:**
- `src/components/service/ServiceApp.tsx:2594,2613`
- `src/app/(dashboard)/ordens/[id]/OrdemDetalheClient.tsx:124`
- `src/components/pcp/PCPDetalheModal.tsx:132`

## 1.2. Concorrência & Dinheiro

### M1. Race conditions remanescentes em geração de números (10+ pontos)
Migration 259 criou `venda_numero_seq`, mas estes pontos ainda usam `MAX(...) + 1`:

| Arquivo:linha | Campo |
|---|---|
| `src/app/api/ordens/route.ts:213` | `numero_ordem` |
| `src/app/api/ordens/proximo-numero/route.ts:14` | `numero_ordem` |
| `src/lib/reposicao-automatica.ts:186` | `numero_ordem` |
| `src/lib/vendas-aprovar.ts:394,536` | venda (mesmo após sequence existir) |
| `src/app/api/vendas/[id]/route.ts:728` | venda |
| `src/app/api/estoque-comercial/converter/route.ts:93` | venda |
| `src/app/api/produtos/setup/route.ts:26,32` + `route.ts:541` | SKU |
| `src/app/api/rfid/imprimir/route.ts:36` | **EPC RFID** (colisão silenciosa = peça com EPC duplicado) |
| `src/app/api/produtos/[id]/imagens/route.ts:132` | nome de imagem |

**Fix:** criar SEQUENCES (`numero_ordem_seq`, `produto_sku_seq`, `epc_rfid_seq`) e usar `nextval()` dentro de transação. Remover todos os `Math.max + 1`/`MAX(...) + 1`.

### M2. Coluna `ouro_peso` vs `ouro_gramas` em `pagamentos_venda` — pagamento em ouro
**Tabela:** `alissonerp.pagamentos_venda`
- Migration 138 criou `ouro_peso`, `ouro_valor_grama`, `ouro_foto_path`
- Migrations 178/181 reintroduziram `source` e referenciam `ouro_gramas`
- Migration 204 admite: *"Migration 181 quebrou o fallback ouro_peso -> ouro_gramas que existia na 178. Dados historicos estao em ouro_peso, nao em ouro_gramas"*

**Impacto:** pagamento em ouro = DINHEIRO. `vw_cofre_ouro` usa `COALESCE(ouro_peso, ouro_gramas)`, mas queries/relatórios que olhem só uma coluna retornam dados parciais.
**Fix:** migration 261 — backfill `ouro_gramas = COALESCE(ouro_gramas, ouro_peso)`, dropar `ouro_peso` (confirmar zero uso no código primeiro). Atualizar `vw_cofre_ouro`.

### M3. Migrations 178 e 181 são quase idênticas com BACKFILL DIFERENTE — corromperam histórico financeiro
**Arquivos:** `supabase/migrations/178_financeiro_aging_source_cofre.sql`, `181_financeiro_aging_source_cofre.sql`
Ambas adicionam coluna `source`, criam UNIQUE em `gateway_id`, adicionam FK em `fin_conciliacoes`. Mas **a 181 fez backfill diferente** (`gateway_payload::text LIKE '%webhook%'` além do gateway_id). Linhas que tinham `source='manual'` viraram `'webhook_mp'` na segunda passada.
**Impacto:** Coluna `source` em `pagamentos_venda` está com dados misturados. Conciliação bancária fica inconsistente.
**Fix:** auditar dados de `source`, decidir lógica correta, re-rodar idempotente. Renomear uma das migrations para `_replaced_by_181.sql` ou remover do fluxo.

---

### M4. 38 migrations duplicadas no mesmo número (ordem não-determinística)
Números duplicados: `086, 111, 130, 134, 135, 136, 137, 138, 140, 154, 155, 156, 157, 158, 162, 167, 168, 169, 172, 173, 176, 178, 179, 186, 202, 203, 204, 231, 233, 241, 242 (3×!), 243, 244, 245, 246, 247, 248`.

Exemplo: `138_pagamento_ouro.sql`, `138_produto_tipo_item.sql`, `138_saldo_gerente_credito.sql` — três migrations diferentes com mesmo número. Postgres roda em ordem alfabética interna, dependente da ferramenta.

**Caso real:** migration 167 colidiu (`167_fix_trigger_preco_produto.sql` vs `167_sync_public_vendas_to_erp.sql`) — se a "fix" rodar antes da "sync", o trigger novo dispara em registros que ainda nem foram inseridos.

**Fix:**
1. Renumerar duplicadas em ordem cronológica via `git log --diff-filter=A`.
2. Adicionar lint pre-commit que rejeita PR com número já em uso.
3. Adicionar coluna `aplicada_em` em `supabase_migrations` se não tiver.

### M5. Sync `public.vendas` ↔ `alissonerp.vendas_erp` com drift de 104 linhas
**Tabelas:** `public.vendas` (14.444 rows) + `alissonerp.vendas_erp` (14.548 rows)
**Triggers de sync:** `trg_sync_venda_insert_from_public`, `trg_sync_venda_update_from_public`, `trg_sync_item_venda_insert_from_public`.
**Migrations envolvidas:** 109 (backfill), 115 (fix), 117 (fix faltantes), 118 (bypass blindagem), 167 (backfill novo), 110 (fix exception), 116 (blindar).

**Pior:** `public.itens_venda` (75.961 rows) vs `alissonerp.itens_venda_erp` (37.758 rows) — **gap de ~50%**. Mig 117 tentou corrigir, claramente não pegou tudo. Comissão/fiscal calculados no ERP podem estar incompletos.

**Fix:** decidir source-of-truth único. Migrar para arquitetura "alissonerp escreve, public é VIEW". Antes disso, backfill controlado com diagnóstico antes/depois.

### M6. `itens_venda_erp.produto_id` sem FK (e mais 5 colunas similares)
Sem FK cross-schema declarada em: `itens_venda_erp.produto_id`, `ordens.cliente_id`, `ordens.vendedor_id`, `vendas_erp.cliente_id`, `vendas_erp.vendedor_id`, `contas_receber.cliente_id`.
**Impacto:** produto_id apontando para produto deletado/inexistente fica órfão silenciosamente.
**Fix:** FK NOT VALID (não revalida histórico). Migration 260 já fez para `orcamentos.vendedor_id` — replicar.

### M7. `cofre_ouro_baixas` sem trigger de movimentação dupla
**Tabela:** `alissonerp.cofre_ouro_baixas` (criada na mig 202)
Não há trigger garantindo correspondência com `movimentacoes_estoque`. CLAUDE.md §3: *"Movimentacoes: SEMPRE dupla-entrada"*.
**Impacto:** saída de ouro do cofre pode não ter contrapartida — quebra "toda grama conta".
**Fix:** trigger AFTER INSERT chamando `fn_criar_par_movimentacao`.

---

### M8. `public.orcamento` (legado, 78 refs) coexiste com `alissonerp.orcamentos` (novo, 14 refs)
Migration 120 criou a nova; a antiga em public ainda tem triggers ativos (`trg_aprovacao_orcamento`, `trg_gerar_numero_orcamento`, `fn_inicializar_orcamento`).

**Pior:** migration 260 (hardening recente) protege apenas `alissonerp.orcamentos`. UI pode estar lendo/gravando na errada — bug "orçamento perdia snapshot" pode ter origem aqui.

**Fix:** auditar cada uma das 78 refs ao `public.orcamento`. Migrar para `alissonerp.orcamentos`, deletar ou criar VIEW de compatibilidade. Trigger BEFORE INSERT que recuse novas linhas na legada.

### M9. Optimistic locking só em 3 rotas
Padrão `client_updated_at` (ADR 0006) só implementado em: `orcamento/[id]`, `vendas/[id]`, `site/test`.

**Faltando em:** `produtos/[id]`, `insumos/[id]`, `pcp/[id]`, `service/[id]`, `crediario/[id]`, `tarefas/[id]`, `compras/[id]`. Dois usuários editando o mesmo produto = último ganha sem aviso.
**Fix:** adicionar `WHERE id = ${id} AND updated_at = ${client_updated_at}` em PATCH/PUT críticos; retornar 409 quando não match.

# 2. ALTOS — bug funcional / debt grave

## 2.1. API & Backend

### A1. Validação Zod só em 10 rotas (228 fazem `await req.json()` direto)
**Padrão problemático:** cast TypeScript "as" + `parseInt`/`Number` sem checar NaN. NaN vira NULL em `WHERE id = ${id}` (postgres pode aceitar) — query retorna linhas inesperadas.
**Exemplos sentinela:** `pcp/saida`, `distribuicao/*`, `service/*`, `precificacao/*`, `produtos/*`, `tarefas/*`.
**Fix:** padronizar `defineRoute({ inputSchema })`. Migração incremental por módulo.

### A2. N+1 queries em loops sobre arrays (50 arquivos)
**Casos críticos:**
- `vendas/route.ts:494-537` — 3-4 queries por item de venda
- `purificacao/route.ts:228-244` — INSERT em loop
- `distribuicao/[id]/saida/route.ts`, `pcp/saida/route.ts`
**Fix:** `sql\`INSERT INTO ... VALUES ${sql(rows)}\`` ou `UNNEST`.

### A3. `vendas/cliente/[id]/historico` sem filtro por consultora
**Arquivo:** `src/app/api/vendas/cliente/[id]/historico/route.ts`
Autentica mas não checa role/escopo. Consultora vê histórico de cliente que pertence a outra consultora. Mesmo em `vendas/[id]/route.ts` (vaza `observacoes_internas`, `total_comissao`, `valor_comissao`).
**Fix:** filtrar por `cliente.vendedor_id = user_vendedor_id` quando role for `consultora`.

### A4. SQL silencioso falha com `parseInt(NaN)`
**Padrão:** `c.local_destino_id = ${parseInt(localIdFilter)}` em `compras/route.ts:26,58` — `parseInt("abc")` retorna NaN, vira NULL no SQL, comparação sempre falsa. Padrão repetido em dezenas de rotas.
**Fix:** validar `Number.isInteger(...)` + retornar 400.

### A5. Resposta inconsistente entre rotas
- `compras/route.ts` POST retorna `normalizeRow(row, ...)` cru
- `insumos/route.ts` POST retorna `rows[0]`
- `lancamentos-avulso/route.ts` retorna `{ id }`
- `vendas/route.ts` retorna `{ id, numero_venda, ...campos planos }`
- `purificacao/route.ts` retorna `{ id, ok: true }`

Frontend tem que adivinhar shape.
**Fix:** padronizar `{ ok: true, data: T }` (já é o padrão do `defineRoute`).

### A6. Geração de números espalhada (`MAX+1`)
Repetida em `vendas/route.ts:485`, `ordens/proximo-numero/route.ts`, `produtos/personalizados/proximo-sku/route.ts`. Ver também M1 (race condition).
**Fix:** centralizar em `src/lib/numeracao.ts` com sequences.
